# D-013 Taskbar strip attached as a child window of Shell_TrayWnd

Accepted · 2026-11-04 · Verified on Win11 26H2 (build 26300, 4K at 200%)
Decision: create the strip as a cross-process child window (`WS_CHILD` with parent `Shell_TrayWnd` or `Shell_SecondaryTrayWnd`) using `WS_EX_LAYERED` + `UpdateLayeredWindow(ULW_ALPHA)`.
Reason: UIPI allows child creation and input; per-pixel alpha lets the taskbar background show through cleanly; the strip stays anchored inside the taskbar without topmost z-order fighting.
Critical implementation constraints:
- Call `ChangeWindowMessageFilterEx(MSGFLT_ALLOW)` for `TaskbarCreated` on the hidden top-level main window (`HWND_MESSAGE` windows do not receive broadcasts).
- Explorer destruction sends only `WM_NCDESTROY`, not `WM_DESTROY`. Re-attach via `WM_NCDESTROY`, `TaskbarCreated`, and a 2 s fallback timer (which also raises above Explorer's delayed `Windows.UI.Core.CoreWindow` sibling).
- Fill transparent pixels with alpha = `1/255` so hits are not passed through; use grayscale text anti-aliasing (ClearType fringes on per-pixel alpha).
- Handle `WM_CONTEXTMENU` locally so right-clicks do not forward to Explorer; position tracking tooltips (`TTF_TRACK | TTF_ABSOLUTE`) owned by the hidden main window.
- Locate the Start button via the child `Start` window rect without UI Automation.
Cost: joins the strip's input queue with Explorer's, so the UI thread must never block.
Rejected: floating topmost window tracking the taskbar rect (z-order fighting and fullscreen hiding issues; kept only as a future fallback if a Windows update breaks child attachment).
